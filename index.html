1

What you actually download

Disk → CPU RAM→ GPU memory

An open-weight model is three files and no program. config.json describes the shape, tokenizer.json holds the vocabulary and merge rules, and model.safetensors holds the numbers. The inference engine (vLLM, llama.cpp, or the few hundred lines of JavaScript running this page) supplies the code that multiplies them.

The shape: config.json

These few numbers decide every tensor size on this page. Change the model at the top and they all change with it.

The numbers: model.safetensors

The file starts with 8 bytes giving the length of a JSON header. The header lists every tensor's name, data type, shape and byte range. Everything after it is raw numbers, back to back. The engine reads the header, then copies each tensor into GPU memory once. This page read the real header from Hugging Face with two small range requests, without downloading the weights.

Precision is a memory decision

The weights ship as bfloat16, which is 2 bytes per number. Quantizing to 8 or 4 bits shrinks the file, and because generating each token means reading every weight once, it also cuts the bytes moved per token. That's why quantized models often generate faster, not just fit in less memory.

2

Text becomes integers

CPU

The model never sees letters. A tokenizer turns your text into integer IDs from a fixed vocabulary of 49,152 entries. It runs on the CPU, usually in Rust or C++, before any GPU work starts. This one uses byte-level Byte Pair Encoding, the same family as GPT-2, Llama 3 and Qwen. Edit the prompt above and everything here updates as you type.

Split off special tokens, then pre-split into words

Chat markers like <|im_start|> are matched literally and get fixed IDs. The rest is cut by a regex into words, each keeping its leading space, plus punctuation runs and single digits. BPE never merges across these cuts.

Replay the merges for one word

Each word starts as raw UTF-8 bytes, each shown as one printable character, so a space appears as Ġ. The tokenizer then repeatedly merges the adjacent pair that ranks highest in its merge list. That list was learned during training by counting which pairs appeared most often, and a lower rank means more common. It stops when no adjacent pair is in the list. Click any word above to replay it.

Look up the IDs

Each final piece is a key in the vocabulary. The result is the only thing sent to the GPU: one integer per token, 4 bytes each.

Each ID picks a row

IDs over PCIerow reads from HBM

The embedding matrix has one row per vocabulary entry: 49,152 × 576. There's no arithmetic in this step. Token ID n means “copy row n”. A prompt of T tokens becomes a T × 576 matrix of floats. These are the actual rows for your prompt, with blue for negative values and red for positive.

The rows aren't random. Training placed tokens that behave alike near each other. Pick a token to see its nearest neighbours among all 49,152 rows by cosine similarity.

4

Where position comes in

SM registers, inside attention

A row lookup knows nothing about order: “dog bites man” and “man bites dog” fetch the same rows. GPT-2 fixed this by adding a learned position vector to each embedding. Llama-family models, including this one, add nothing. Instead, inside every attention layer, they rotate each query and key vector by an angle proportional to its position. This is RoPE, rotary position embedding.

Each 64-number head vector is treated as 32 pairs, and each pair is a point that gets spun. Pair 0 turns a full radian per position, while the last pair barely moves. When a query at position m meets a key at position n, the two rotations partly cancel, so their dot product depends only on the distance m − n.

5

Attention: tokens read each other

weights + KV from HBMmatmuls on tensor cores

The T × 576 matrix now passes through 30 identical layers, each with its own weights. Every layer does two things: attention, where tokens exchange information, and a feed-forward network, where each token is transformed on its own. Here is one layer with the real shapes.

Q, K and V are three matrix multiplies

Each token's vector is multiplied by three learned matrices. The query says what this token is looking for. The key says what this token offers to others looking. The value is what it hands over if chosen. The query is compared with every earlier key by dot product, the scores go through softmax so they sum to 1, and the output is the weighted sum of the values. A token can't look forward: the causal mask hides later positions.

This model has 9 query heads but only 3 key/value heads, so each K/V head serves 3 query heads. This is grouped-query attention, and it makes the KV cache 3× smaller.

6

Feed-forward and the residual stream

most of each layer's weightstensor cores

After attention, each token goes through its own two-step network. It is projected up from 576 to 1,536 numbers twice (a gate and an up projection), the two are combined as silu(gate) × up, and the result is projected back down. That's three matrices holding ⅔ of each layer's weights. Most of a model's parameters, and most of its stored knowledge, sit here. Below are the 1,536 combined values for the last token of your prompt, in the layer you choose.

Nothing is overwritten, only added

Attention and the feed-forward network don't replace a token's vector. They each add a correction to it (x = x + attention(x), then x = x + ffn(x)). That running vector is the residual stream. Its length grows as the layers write into it.

Read the stream early: the logit lens

Apply the final output step to the residual stream after each layer and you see what the model would say if it stopped there. Early layers produce noise, and the answer usually snaps into place in the last third.

7

From a vector to a word

LM head + softmax on GPU4 bytes backdetokenize on CPU

After the last layer, only the final token's vector matters for predicting what comes next. It is normalised and multiplied by the LM head, a 49,152 × 576 matrix. In this model it is the same matrix as the embedding table, read the other way. The result is one score per vocabulary entry: the logits. Softmax turns them into probabilities, and a sampler picks one. Only that one integer has to travel back to the CPU.

Integer back to text

The CPU reverses the tokenizer: ID → vocabulary entry → raw bytes → UTF-8. A token can end partway through a multi-byte character, such as an emoji, so streaming decoders hold incomplete bytes until the character is finished.

8

The decode loop and the KV cache

KV cache lives in HBMone token per pass

Prefill ran all prompt tokens through the layers at once. From here on, the model generates one token at a time, and each new token runs through all 30 layers by itself. It can't be parallelised, because step n + 1 needs the token chosen at step n.

In each layer the new token needs the keys and values of every earlier token. Those never change: a past token's K and V depend only on the tokens before it. So the engine computes them once and stores them. That store is the KV cache. Each step computes K and V for the one new token, appends them, and reads all the rest back.

Turn it off and watch the cost

Without the cache, every step must recompute K and V for the whole sequence: a full prefill per token. The bars are the real per-step times in this tab.

9

Why decode is memory-bound

bandwidthvs compute

Every decode step streams all the weights from HBM into the compute units, roughly 269 MB for this model, to do about 0.27 GFLOP of math. That's about 1 FLOP per byte. An H100 can do about 295 FLOPs in the time it takes to fetch one byte from HBM, so during decode the compute units wait on memory most of the time.

Prefill feeds T tokens through the same weights at once. Each weight fetched is used T times, so intensity rises to about T FLOPs per byte and prefill becomes compute-bound. Batching many users' decode steps together does the same for decode. That's what continuous batching in vLLM and TGI exploits.

Prefix caching: don't prefill twice

KV blocks stay in HBM

Most requests start with the same tokens: a chat template and a system prompt. Their keys and values come out identical every time, because they depend only on the tokens before them. Engines therefore keep the KV cache in fixed-size blocks of 16 tokens and key each block by a hash of its tokens and the hash of the block before it. A block is reused only when everything before it matches too.

Run a prompt, change only the question, and run it again. The shared blocks are skipped, and you can see the real prefill time drop. The default system prompt here is short, so only one block can be shared. Production system prompts often run to thousands of tokens, which is where this pays off: switch to a longer one, run twice, and compare.

One request, every byte

CPUPCIeHBMSM

Your last run, phase by phase. “H100 estimate” is the time the bytes or FLOPs alone would take on one H100 SXM (3.35 TB/s HBM, 989 dense BF16 TFLOPS). It is a floor that ignores kernel-launch overhead, which dominates for a model this small. “This tab” is what actually happened here.

Three things set the speed of inference. The weights must be read once per decode step, which makes HBM bandwidth the limit. The KV cache grows with every token in every request, which makes HBM capacity the limit. Prefill is a big matrix multiply, which makes compute the limit. Quantization, paged attention, continuous batching, prefix caching, speculative decoding and prefill/decode disaggregation each attack one of those three.
