The ideas you need first

No model needed

A language model is a very large pile of numbers and one simple operation repeated over and over. Five ideas are enough to follow the rest of this page.

A vector is a list of numbers that describes something

Here is a colour described by three numbers: how much red, green and blue. That list of three is a vector. Move the sliders: the numbers change the thing they describe.

Language models describe each piece of text the same way, just with far more numbers. Two separate tables are involved, and both are looked up with the same ID number:

  • The vocabulary (in tokenizer.json) only maps IDs to text: ID 3575 is the text “␣capital”. It contains no numbers about meaning.
  • The embedding table (in the model file) gives every ID its own list of 576 numbers. That list is what the model actually works with.

Why 576? It’s a size the model’s makers picked before training, called the hidden size. Bigger means more room to encode meaning, but every matrix grows with it, so the model gets slower and needs more memory. Small models use a few hundred; GPT-2 used 768, Llama 3 8B uses 4,096 and Llama 3 70B uses 8,192. Nobody decided what each of the 576 numbers means either. Training settled on values that make the model good at predicting text, so the numbers end up capturing things like “this is a city” or “this is plural”, spread across many positions at once.

Matrices and tensors are boxes of numbers

A matrix is a grid of numbers, like a spreadsheet: so many rows, so many columns. Tensor is the catch-all word for a box of numbers with any number of directions. Files and code say “tensor” because they don’t care how many directions a box has.

The last row is the trickiest, so here is its shape drawn out. Picture one sheet of numbers per layer. On each sheet, every token is a column, and the column holds 3 heads × 64 = 192 numbers. Stack 30 sheets and you have the keys; the values are a second stack of the same shape. Chapter 10 shows the real numbers.

The one operation: multiply a matrix by a vector

Almost all of the model’s work is this. Take a vector in. For each row of the matrix, multiply the row and the vector number by number and add up the results. That sum is a dot product, and each row gives one output number. The result is a new vector. Click an output to see its arithmetic, and edit the input numbers.

The sizes always follow one rule. A matrix with m rows and n columns needs an input of exactly n numbers, one per column, and gives back m numbers, one per row. Feed it several input vectors side by side and you get that many output vectors in one go. That is how the model handles a whole prompt at once.

To produce a single word, this model performs about 134 million of these multiply-and-add steps.

Weights are the numbers inside the matrices

The numbers in the model’s matrices are its weights, also called parameters. Training adjusted them over trillions of words of text until the model got good at guessing the next word. When you use the model, which is called inference, the weights are frozen: nothing is learned and nothing changes. The 269 MB download is about 135 million of these numbers, and nothing else.

Where the weights come from: forward and backward

Running numbers through a model from input to output is a forward pass. That is all inference is, and all this page ever does.

Training adds a second direction. After each forward pass, the output is compared with the right answer: the word that actually came next in some real text. Then a backward pass (backpropagation) works out, for every single weight, which direction would have made the right answer a little more likely. Every weight gets nudged that way, and it repeats. SmolLM2 went through this with 2 trillion tokens of text. Try it on a model with 9 weights:

A real model does exactly this, just with 135 million weights instead of 9, and with the error passed back through all 30 layers instead of one. When training is finished, the weights are frozen and published. Using the model only needs the forward half: no comparing, no nudging. That’s why running a model is so much cheaper than training it.

The machine: where the numbers live and move

A server running a model has two very different processors. The CPU handles text and decisions. The GPU does the giant multiplications. Each has its own memory, and moving numbers between places takes time.

The key fact for everything that follows: a modern GPU can multiply numbers much faster than it can fetch them from its own memory. Much of what makes inference fast or slow comes down to how many bytes have to move, not how much arithmetic there is. What you actually download

Disk → CPU RAM→ GPU memory

A downloaded model isn’t a program. It is three files: a short description of the model’s shape, a dictionary of text pieces, and one big file of numbers. The software that runs it, called an inference engine, brings the code. Here it is a few hundred lines of JavaScript; on servers it’s vLLM, llama.cpp or similar.

The shape: config.json

A handful of sizes fixes every matrix in the model. For example, hidden_size of 576 means every token is a vector of 576 numbers, and num_hidden_layers of 30 means the tower in the 3D view is 30 layers high.

The numbers: model.safetensors

This file is a table of contents followed by the numbers themselves, packed back to back. The table of contents lists every matrix by name and shape. Laid out as a tree, it gives the model’s whole anatomy. The key thing to see: each of the 30 layers has its own copy of the same set of matrices. The shapes are identical, the numbers inside are different.

Go deeper: the file format and number precision

A safetensors file starts with 8 bytes giving the length of a JSON header. The header lists each tensor’s name, data type, shape and byte range; raw numbers follow. An engine reads the header, then copies each tensor into GPU memory once at startup. This page read the real header from Hugging Face with two small HTTP range requests, without downloading the weights.

The weights are stored as bfloat16, 2 bytes per number. Quantizing to 8 or 4 bits shrinks the file. Because generating each token means reading every weight once, it also cuts the bytes moved per token, so quantized models often generate faster, not just fit in less memory.

2

Text becomes numbers

CPU

The model can only do arithmetic, so your text first has to become numbers. The model comes with a fixed dictionary of 49,152 text pieces called tokens. Common words are a single piece, rarer words are built from several, and every piece has an ID number. The tokenizer chops your text into these pieces and looks up their IDs. It runs on the CPU, before the GPU does anything.

Look inside the dictionary

Search the model’s vocabulary, or browse parts of it. On this page ␣ marks a space and ↵ a new line. Spaces are part of tokens: ␣cat (as in “the cat”) is a different entry from cat at the start of a line. The full list is in tokenizer.json on Hugging Face (a 2 MB text file), and Tiktokenizer lets you compare how different models split the same text.

Step 1: cut the text into words

First the text is cut at spaces and punctuation, keeping each space attached to the word after it. Chat markers like <|im_start|>, shown in black, are special tokens with fixed IDs: they tell the model who is speaking. Edit the prompt above and watch these update.

Step 2: glue letters into dictionary pieces

This is the part that isn’t obvious: the tokenizer does not search the dictionary for your word. It follows a recipe:

  1. Break the word into single letters (strictly, bytes). Every single byte is in the dictionary, so this always works, even for emoji or made-up words.
  2. Look at each pair of neighbours. The dictionary file also stores a ranked list of 48,900 glue rules, such as “Ġ + t → Ġt” as rule #0. They were learned in training by repeatedly gluing the most common pair in a huge pile of text. Apply the highest-ranked rule that matches.
  3. Repeat until no rule matches. Every glued piece is itself a dictionary entry, so whatever is left has an ID.

Common words get glued all the way into one piece. Rare or made-up words run out of rules partway and stay as several pieces. This method is called Byte Pair Encoding. In this view a space appears as Ġ, which is how the dictionary file writes it. Try the examples:

Step 3: look up the IDs

Each final piece is a dictionary entry with an ID. This list of integers, 4 bytes each, is all that gets sent to the GPU.

Each ID becomes a vector

IDs over PCIerow reads from HBM

An ID like 5992 is just a label, as meaningless as a locker number. So the model swaps each ID for a vector of 576 numbers that it learned during training: the token’s embedding. The vectors sit in one big table with a row per vocabulary entry, and ID 5992 simply means “take row 5992”. There is no calculation in this step, just lookups.

How to read this: the strip on the left is the whole table, all 49,152 rows squeezed to fit, with teal marks at the rows your prompt uses. On the right, each line is one of your tokens, with its 576 numbers drawn as coloured bars: blue for negative, red for positive, paler for close to zero. The patterns look random to us. To the model they encode what the token means and how it is used.

One way to check that these numbers mean something: tokens used in similar ways get similar vectors. Pick a token to find the rows closest to it in the table.

Go deeper: shapes and sizes

The embedding table is a 49,152 × 576 matrix. A prompt of T tokens becomes a T × 576 matrix: one row per token. On a GPU this step is a gather: it reads T rows of 576 × 2 bytes from HBM. The similarity search above uses cosine similarity, the dot product of two vectors divided by their lengths, so 1 means “same direction”.

4

How the model knows word order

inside attention, on the GPU

Looking up vectors loses the word order: “dog bites man” and “man bites dog” fetch exactly the same three vectors. The model needs to know which word came where, or at least how far apart two words are.

Its trick is like clock hands. Picture each token’s vector as a clock hand. Before tokens are compared, every hand is turned by an amount that depends on the token’s position: the token at position 1 is turned a little, position 2 a little more, and so on.

When the model compares two tokens, it effectively looks at the angle between their hands. That angle depends only on how far apart the tokens are, not on where they sit in the text. Words three apart look the same to the model at the start of a sentence or a thousand words in. The widget below uses the model’s real vectors. Move the positions, then shift both tokens later and watch the angle between them stay put.

Go deeper: RoPE in detail

This is rotary position embedding (RoPE), used by Llama, Qwen, Mistral and this model. GPT-2 did something simpler: it added a learned position vector to each embedding. RoPE adds nothing to the embedding. Instead, inside every attention layer, it rotates the query and key vectors.

Each 64-number attention vector is split into 32 pairs, and each pair is a point that gets rotated. Pair 0 turns 1 radian (about 57°) per position. Each later pair turns more slowly, down to pair 31, which barely moves. Fast pairs tell nearby words apart; slow pairs still change measurably across thousands of positions. Because a rotation by angle a and another by angle b meet at angle a − b, the query·key score depends only on the distance between positions.

5

The transformer: talk, think, repeat

one layer’s weights at a timeGPU

Everything between the embeddings and the final scores is one block, repeated 30 times. Each block has two halves. First the tokens talk: attention lets each token gather information from the tokens before it. Then each token thinks on its own: the feed-forward network processes what it just gathered. Both halves add their result to the token’s running vector, and the next block starts from there.

That repeated block is what makes this a transformer, the design behind GPT, Llama, Qwen, Claude and this model. Press play to watch a short sentence go through it.

Why both halves? They do different jobs, and each needs the other:

  • Attention moves information between tokens, but it only mixes and re-weights what is already there.
  • Feed-forward transforms each token, applying patterns stored in its weights, but it can’t see the other tokens.
  • Alternating them 30 times lets the model build up meaning step by step. Roughly, early layers sort out nearby words and grammar, middle layers combine facts, and late layers settle on the next word. The logit lens in chapter 7 shows this with real numbers: the right answer usually appears only in the last third.

The next two chapters zoom into each half. Chapter 9 replays this loop with the real numbers from your prompt.

Go deeper: where the name comes from

The transformer was introduced in 2017 in the paper “Attention Is All You Need”, for translation. That original had two stacks: an encoder that read the whole source sentence and a decoder that wrote the translation. Chat models keep only the decoder half and are called decoder-only transformers. They read left to right, each token can only attend to earlier tokens, and they are trained to predict the next token.

Each block also normalizes the vector before each half (RMSNorm), and adds each half’s output back to its input (the residual connection). Without those two details, stacks of 30 or 80 layers would be very hard to train.

6

Attention: words look at each other

weights + KV from HBMmatmuls on tensor cores

To understand “it” in “the cat sat because it was tired”, the model has to find what “it” refers to. Attention is how each token gathers information from the tokens before it. The vectors now pass through 30 layers, and each layer starts with an attention step.

It works like a library search. Each token makes three new vectors by multiplying its own vector by three weight matrices:

  • a query: what am I looking for?
  • a key: what do I contain? This is like a book’s title.
  • a value: what will I hand over if picked? This is like the book’s contents.

Each token compares its query with the key of every earlier token (a dot product). Better matches get a bigger share of its attention, with shares adding up to 100%. The token then takes that mix of the earlier tokens’ values. A token can never look at tokens after it, because when generating text those don’t exist yet.

Is this per layer? Yes. Each of the 30 layers has its own three matrices for this, plus a fourth (o_proj) that combines the results: 4 attention matrices × 30 layers = 120 separate matrices. They’re the four light tiles in every layer of the 3D model and the self_attn group in chapter 1’s anatomy. Every layer does the same steps with different numbers, so each layer looks for different things.

Heads: one query, cut into slices

One more detail, because it explains the odd matrix sizes. The query isn’t used as one long list of 576 numbers. It is cut into 9 slices of 64, and each slice does its own attention, separately from the others. Each slice is called a head. Nine heads means nine independent “searches” per layer: one head might track the previous word, another the subject of the sentence. That’s why the grid below changes when you change Head.

Keys and values are cut the same way, but there are only 3 slices of them (3 × 64 = 192 numbers). Each key/value slice is shared by 3 query heads. That saves memory, and it’s exactly why k_proj and v_proj are 192 × 576 while q_proj is 576 × 576. Each word thinks on its own, and keeps a running total

most of each layer’s weightstensor cores

After gathering context with attention, each token is processed on its own by a small network called the feed-forward network. It stretches the token’s 576 numbers out to 1,536, filters them, and squeezes them back to 576. These matrices hold 75% of each layer’s weights, and this is where much of the model’s learned knowledge is applied.

How to read this: each thin bar is one of the 1,536 intermediate numbers for the last token of your prompt, in the layer you pick. Most sit near zero and a few spike. Each spike is a learned pattern that recognised something in this context and fired.

Nothing is replaced, only added

Neither attention nor the feed-forward step overwrites a token’s vector. Each adds its result to the vector instead, like adding notes to a running total. That running vector is the residual stream, and it carries everything the token has picked up so far. How to read this: each line is one token of your prompt, showing how long its vector gets after each layer. The highlighted line is the last token, the one that will predict the next word.

Peek at the model’s guess after every layer

The running total can be read at any point to see what the model would say if it stopped there. This trick is called the logit lens. Early layers produce nonsense, and the real answer usually appears in the last third.

Go deeper: SwiGLU

The feed-forward block uses two “up” projections from 576 to 1,536, called gate and up. They are combined as silu(gate) × up, where SiLU is a smooth function that passes positive values and squashes negative ones. A down projection then maps back to 576. Each layer is normalised first with RMSNorm, which rescales a vector to a standard length so the numbers don’t grow out of control across 30 layers.

8

Picking the next word

scores on the GPU4 bytes backtext on the CPU

After the last layer, the model compares the last token’s vector against every one of the 49,152 dictionary entries and gives each a score. These scores are called logits. Softmax turns the scores into percentages. Then the computer rolls weighted dice: a token with 80% wins 8 times out of 10. The winner is the next token, and the whole process repeats with it added to the text.

You control the dice:

  • Temperature below 1 makes the favourite even more likely (safer, more repetitive). Above 1 evens the odds (more varied, more mistakes). At 0 the model always takes the top choice, called greedy.
  • Top-k only allows the k highest-scoring tokens.
  • Top-p only allows the smallest group of top tokens whose chances add up to p.

Click any word of the answer above to see the choice behind it. Click another candidate below to swap it in and continue from there.

From ID back to text

Only the winning ID, a single number, goes back to the CPU. The CPU reverses the tokenizer: it looks up the dictionary entry, turns it into bytes, and the bytes into characters.

Go deeper: the LM head

The scores come from one last matrix multiply: the final vector (normalised) times the LM head, a 49,152 × 576 matrix. In this model the LM head is the embedding table itself, read the other way round: the score for each token is the dot product between the final vector and that token’s embedding. A token can end partway through a multi-byte character such as an emoji, so streaming decoders hold incomplete bytes until the character is complete.

One word at a time, with notes

KV cache lives in GPU memoryone token per pass

Your whole prompt went through the model in one go; this is called prefill. The answer can’t be produced that way. Each new token depends on the one chosen before it, so the model runs once per token, feeding in the token it just picked. This loop is called decode.

On every pass, the new token needs to look back at all earlier tokens (chapter 6), using their keys and values. Those never change once computed, so instead of recomputing them on every pass the model keeps them, like notes, in GPU memory. These notes are the KV cache. Each pass adds one column of notes for the new token, in every layer.

How to read this: each column is one token and each row is one layer. Every small cell holds that token’s key and value for that layer. Amber cells came from your prompt; pink cells were added one by one as the answer was written.

Why writing is slower than reading

memory speedvs arithmetic speed

Think of the GPU as a very fast chef with a pantry down the hall. The ingredients are the model’s weights. To write each new word, the chef must fetch every ingredient (all 269 MB), does a few seconds of chopping, then fetches everything again for the next word. The chef spends most of the time walking, not cooking. That is what memory-bound means.

Reading the prompt is different. The chef fetches each ingredient once and uses it for all the prompt’s tokens at once, so there is lots of chopping per trip. That is compute-bound, and it’s why prefill handles hundreds of tokens in the time decode writes a few.

Servers fix the walking problem by cooking many orders per trip: they batch many users’ next words into one pass, so each weight fetched is used for all of them. Drag the sliders and watch the dots move toward the flat “compute” part of the chart, where the chef finally stops waiting.

How to read the chart: left to right is how much arithmetic is done per byte fetched from memory. Up is how fast the GPU can go. The sloped part of the roof is the memory limit and the flat part is the arithmetic limit. A dot on the slope is waiting on memory. An H100 needs about 295 operations per byte before its arithmetic units are kept busy. One user’s decode does about 1.

Go deeper: arithmetic intensity

Arithmetic intensity is FLOPs divided by bytes read. A decode step for one sequence does about 2 FLOPs per weight (a multiply and an add) and reads each weight once at 2 bytes, so intensity is about 1. An H100 SXM moves 3.35 TB/s from HBM and computes about 989 trillion bf16 FLOPs per second, so it needs about 295 FLOPs per byte to be compute-bound. Prefill with T tokens, or decode with a batch of B sequences, multiplies the intensity by roughly T or B. Attention over the KV cache adds bytes that batching can’t share, because each sequence has its own cache.

12

Reusing notes between requests

KV blocks stay in GPU memory

Most requests to a chatbot start with the same text: the hidden instructions (the system prompt) and the chat formatting. Their KV-cache notes come out identical every time, because each token’s notes depend only on the text before it. So servers keep those notes after a request ends and reuse them for the next request that starts the same way, skipping that part of prefill. This is prefix caching.

Notes are kept in blocks of 16 tokens. A block is reused only if it and everything before it match exactly. Change one word early on and every block after it has to be recomputed. That’s why production apps keep their system prompt identical, byte for byte.

Try it: run a question, then press “Ask a different question”. Only the question changes, so the shared blocks are reused and the time to the first word drops. The default system prompt is short, so only one block can be shared. Switch to the longer one to see a bigger effect.

The whole trip, in one table

CPUPCIeHBMSM

Your last request, step by step: where each step ran, how much data it moved, and how long it took. “This tab” is what actually happened in your browser. “H100 estimate” is the least time the same work could take on one data-centre GPU, counting only memory and arithmetic limits.

Three limits set the speed of inference:

  • Memory speed: every new word means reading all the weights again.
  • Memory space: every word of every conversation adds to the KV cache.
  • Arithmetic: reading a long prompt is one big multiplication.

Every speed-up you’ll read about attacks one of these: quantization, paged attention, batching, prefix caching, speculative decoding, and splitting prefill and decode onto different GPUs.
